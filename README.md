# Election Wallpaper (Pass 2 — live-ish data)

A live-desktop wallpaper that shows election status (President / Senate / House / Governor)
on a US map, built as a self-contained HTML/CSS/JS page.

**On data sources:** none of the purpose-built polling aggregators (PollingSource, Cook
Political Report, FiftyPlusOne) offer a free public API — all three require a paid
subscription, confirmed by hitting them directly. A "Decision Labs" API that looked free
turned out to return fabricated placeholder polls (`"sources":["seed_data"]`) attached to
real pollster names — not usable. What *is* real, free, and current is Wikipedia's
`Predictions` tables on the yearly election articles, which aggregate the same forecasters'
published ratings (Cook, Inside Elections, Sabato, Race to the WH, RCP, Fox, VoteHub, Silver
Bulletin, and others). That's what this pass uses. See `scripts/fetch_live_data.js`.

**Candidate names, headshots + best poll (Senate/Governor):** each individual race's own
Wikipedia article (e.g. "2026 United States Senate election in Michigan") has two useful
things beyond the consensus-rating table:
- The `{{Infobox election}}` at the top of the article: `nominee1`/`nominee2` (or
  `candidate1`/`candidate2`) with the real disambiguated article title per candidate
  (`Mike Rogers (Michigan politician)`, not just "Mike Rogers" — matters for name
  collisions), a raw Commons image filename (`image1`/`image2`), `party1`/`party2`, and
  `before_election` (the actual outgoing officeholder, a specific person — used for a
  genuine incumbency check, not just "this candidate's party currently holds the seat").
  `parseInfoboxCandidates()` turns this into `race.candidates: [{name, articleTitle,
  party, imageUrl, isIncumbent}, ...]`. Headshot URLs are built directly from the Commons
  filename via `Special:FilePath/{filename}?width=80` — no second API call needed.
  Covers nearly every rated race (33/35 Senate, 36/36 Governor) since every article has
  an infobox, even when there's no polling data yet.
- A real "Aggregate polls" table with named poll-aggregator sources (270toWin, Decision
  Desk HQ, FiftyPlusOne, RealClearPolitics, etc.) and each candidate's raw percentage.
  `parseBestPoll()` filters out primary-only tables and "Hypothetical polling" collapsed
  sections (which poll candidates who never actually became the nominee — an earlier bug
  let a stale hypothetical matchup outrank the real one), and keeps whichever aggregator
  has the most recently updated number, giving `race.bestPoll: {source, date, margin,
  leaderParty, candidatePcts: {D, R}}`. Only exists where the race actually has that
  table — genuinely safe races usually don't get independent polling — so this part
  stays best-effort (~11/35 Senate, ~9/36 Governor); races without it still get the
  candidate photos/names, just no live percentages.

The race card renders this as a two-column candidate comparison: name, headshot,
party badge (+ incumbent flag when applicable), and that candidate's poll percentage
per side. Governor already goes through the same `attachCandidatesAndPolls()` call as
Senate (36/36 races have it).

**House candidates + headshots** work the same way but need a different fetch shape,
since House races don't have their own per-race articles: multi-district states publish
"2026 United States House of Representatives elections in {State}" (plural) with each
district's own `{{Infobox election}}` nested under a `== District N ==` heading;
single-district (at-large) states publish the singular "...election in {State}" with the
infobox directly at the top, same shape as Senate/Governor articles. `attachHouseCandidates()`
batch-fetches all 50 state articles, slices out each district's own section
(`extractDistrictSection()`), and runs the same `parseInfoboxCandidates()` /
`parseBestPoll()` on that slice — 435/435 districts got candidate data on the last run.

**Monetization note:** intent is free wallpaper + a tip-jar credit, not a paywall — keeps
things simple since the underlying data is Wikipedia (CC BY-SA, attribution required,
already given above) republishing others' forecaster methodology. Tip-jar link/handle
still needs to be added to the UI once decided.

## What's here

- `index.html` / `style.css` / `app.js` — the wallpaper itself.
- `data/us-states-paths.json` — precomputed Albers-USA-style SVG paths for all 50 states +
  DC (Alaska/Hawaii inset bottom-left), derived from Leaflet's public-domain `us-states.js`
  GeoJSON.
- `data/us-districts-paths.json` — same projection, at the 435-congressional-district
  level, generated by `scripts/project_districts.js` from Census TIGER cartographic
  boundaries. House mode renders this layer instead of the state layer; other modes show
  state boundaries only (with district paths hidden).
- `data/sample-<mode>.json` — static placeholder data (Pass 1 fallback), used automatically
  whenever `dataUrl` is blank or a live fetch fails.
- `data/live-<mode>.json` — **real** data, regenerated by running
  `node scripts/fetch_live_data.js`:
  - **Senate / Governor**: consensus of Wikipedia's forecaster-rating tables, mapped to our
    `safe/likely/lean/toss-up` buckets. `dataType: "rating"` — these are published
    predictions, not raw poll numbers, and the UI says so.
  - **House**: full 435-district map (`data/us-districts-paths.json`, sourced from the
    Census Bureau's `cb_2025_us_cd119_500k` cartographic boundary file, projected through
    the same Albers pipeline as the state map and simplified with Ramer-Douglas-Peucker so
    it's ~300KB instead of ~7MB). Boundaries reflect at least the Texas/Missouri/North
    Carolina/Ohio/California mid-decade redraws (file is dated April 2026, after those);
    Louisiana's (May 2026) and Alabama's (finalized June 2026, after prior litigation) may
    still be pre-redraw — no free source was confirmed caught up to those two. Each
    district is shaded by its real **Cook PVI** (scraped from Wikipedia's "Cook Partisan
    Voting Index" article's full by-district table) — a structural partisan-lean number,
    not a poll or forecast. Districts within Wikipedia's own "swing seat" definition
    (|PVI| ≤ 5) render in full color on the existing safe/likely/lean/slight/toss-up scale;
    everything else (the ~80% of safe districts) renders muted — 80% neutral grey mixed
    with a 60%-strength tint of that party's Safe color, so the ~90 competitive districts
    read as signal against a quiet backdrop instead of 435 equally-loud shapes. The summary
    card separately reports the real national **generic-ballot polling average**, scraped
    from the House elections article's Opinion polling section.
  - **President**: no 2026 presidential race exists, so instead of a forecast this mode
    shows the real, certified **2024 results** (via Decision Labs' `/api/elections/2024`
    endpoint, verified against known results — this is the one part of that API that
    isn't fabricated, see the "Decision Labs" caveat above). Labeled explicitly as
    "2024 result — most recent presidential election (next is 2028)," `dataType:
    "historical-result"`, not styled as a live race.
- `LivelyProperties.json` — the settings panel Lively Wallpaper generates automatically.
- `data/history-<mode>.json` — one signed "sentiment" scalar per calendar day (Senate/
  Governor: net seat swing vs. incumbents; House: generic-ballot margin; President has
  no history file since it's a static historical result), appended by `updateHistory()`
  in `fetch_live_data.js` on every run. Re-running same-day (e.g. a news-alert refresh)
  overwrites that day's entry rather than adding a second one, so the series is one
  reading per day, not one per scrape. Capped at 120 days. Backfilled once from
  `logs/refresh.log`'s historical run output when this feature was added (2026-09-12);
  going forward it's self-sustaining. Rendered as the "Momentum" bar chart, bottom
  right of the wallpaper.

## Refreshing live data

```bash
node scripts/fetch_live_data.js
```

Re-run this whenever you want fresher ratings — Wikipedia's tables update on the editors'
own schedule (usually within a day or so of each forecaster's own update). Nothing here
re-runs it automatically yet; see "Next passes."

**Gotcha already hit once:** `{{USRaceRating|...}}` templates take an optional third
parameter (`|flip`) marking a seat expected to change party control — e.g.
`{{USRaceRating|Lean|D|flip}}`. An earlier version of the parser's regex captured that
whole `D|flip` chunk as "the party," which matched neither `D` nor `R`, so every rating on
a `flip`-tagged row was silently dropped. That undercounted or completely zeroed out races
Wikipedia's own editors had a real, current rating for (North Carolina came out `no-race`;
Texas was missing 2 of its 12 forecaster ratings). Fixed by capturing only up to the next
`|`. Worth remembering if another template parameter gets added later.

**Second gotcha:** not every state's per-race article follows the generic `"2026 United
States Senate election in {State}"` naming pattern — Ohio's is `"2026 United States Senate
special election in Ohio"` (filling Vance's old seat; Husted is the appointed incumbent).
The real pipeline never has this problem because `extractStateName()` pulls `articleTitle`
straight from the actual wikilink in the Predictions table row rather than constructing a
guessed title — but any one-off debugging script that reconstructs the title from a state
name + fixed template string (as opposed to reusing `race.articleTitle`/`ratingsByState[usps].articleTitle`)
will silently fetch a 3-line redirect stub instead of the real article and find nothing.
Any other special election added to a future cycle will have the same shape.

## Try it locally

Any static file server works (fetch() needs http:, not file:):

```bash
python -m http.server 8420 --directory R:/Rookworks/ElectionWallpaper
```

Then open `http://localhost:8420`.

## Load it in Lively Wallpaper

1. Install [Lively Wallpaper](https://www.livelywallpaper.io/) (free).
2. Right-click the Lively library → **Add Wallpaper** → **Website (folder)** → pick this
   `ElectionWallpaper` folder (the one containing `index.html`).
3. Lively reads `LivelyProperties.json` automatically and shows a settings panel for this
   wallpaper (gear icon).
4. Set the wallpaper active. It reads the bundled `data/live-*.json` by default; re-run the
   fetch script periodically (or point `dataUrl` elsewhere) to keep it current.

The same `index.html`/`LivelyProperties.json` pairing is portable to Wallpaper Engine's
web wallpaper support with only minor property-schema differences, if that's preferred
instead.

## Normalized data schema

```json
{
  "updatedAt": "2026-08-24T14:00:00Z",
  "source": "Wikipedia (aggregated forecaster ratings: ...)",
  "mode": "senate",
  "summary": { "demSeats": 12, "gopSeats": 16, "control": "Republican", "confidence": "consensus of published forecaster ratings (not raw polling)", "unit": "rated seats" },
  "races": [
    {
      "id": "MI-senate", "state": "MI", "status": "toss-up",
      "margin": null, "leaderParty": null, "dataType": "rating", "raterCount": 12,
      "trend": []
    }
  ]
}
```

`status` is one of `safe-d`, `likely-d`, `lean-d`, `slight-d`, `toss-up`, `slight-r`,
`lean-r`, `likely-r`, `safe-r`, `no-race` (state not in play this cycle for that office).
`slight-d`/`slight-r` are a cosmetic split of what used to be one flat `toss-up` bucket
(avg forecaster score magnitude 0.15–0.5): it catches races where a majority of raters
still say Tossup, but every rater who *does* lean picks the same side (e.g. Iowa: 7/12
Tossup, the other 5 all lean R; Michigan: 7/12 Tossup, the other 5 all lean D) — different
from a genuine even split (e.g. Alaska: 11/12 Tossup). `leaderParty` stays `null` for all
three of `slight-d`/`toss-up`/`slight-r`, same as the old flat bucket, so this split is
purely a label/color change and never affects `demNet`/`gopNet` or hold/pickup — only
`lean` and above (avg ≥ 0.5) count as a confident-enough projection to move those numbers. Sample-data races
(Pass 1 fallback) additionally carry a real numeric `margin`/`pollCount`/`trend` since
those are synthetic; live rating-sourced races leave those `null`/empty rather than invent
precision the source doesn't have. Senate/Governor races additionally carry
`incumbentParty` (scraped from the same table) so hold/pickup can be shown per race. House
is district-level (`granularity: "district"` on the payload, `id` like `"OH-13"` instead of
a state code) and each race carries `pviMagnitude`, `incumbentParty` (current
representative), and `competitive` (|PVI| ≤ 5) — the frontend uses `competitive` to decide
full-color vs. muted rendering, not `status` alone.

**Senate/Governor summary panel shows net change, not raw totals.** `summary.demNet` /
`gopNet` is the projected pickup/loss for each party versus whichever party currently
holds each *rated* seat (a Safe-R seat held by a retiring Republican is a hold, net 0; a
Likely-D seat currently held by a Republican is a D pickup, contributing +1/-1). Toss-ups
and non-flips contribute nothing. `summary.demSeatsBefore` / `gopSeatsBefore` are the real
current full-chamber composition, scraped straight from the same Wikipedia article's
infobox (`seats_before1`/`seats_before2`, independents folded into the party they caucus
with) rather than hardcoded — `demSeatsProjected` / `gopSeatsProjected` is baseline + net.
`summary.control` reflects that projected full-chamber majority, not just who's ahead
among the rated subset. House and President summaries still use plain `demSeats`/
`gopSeats` totals (House already reports actual current composition, not a projection;
President is a historical result) — the frontend (`app.js`) branches on whether
`summary.demNet` is present to decide which format to render.

## Configurable properties (Lively panel)

| Property | Purpose |
|---|---|
| `dataUrl` | Data source. `{mode}` is replaced with `president`/`senate`/`house`/`governor`. Defaults to `data/live-{mode}.json`; blank it to force the static sample files. |
| `defaultMode` | Which tab is active on load. |
| `refreshMinutes` | Auto re-fetch interval (default 360 = 6h) — re-reads whatever `dataUrl` currently points to; doesn't itself re-run the Wikipedia scrape. |
| `theme` | `dark` / `light`. |
| `compact` | Smaller cards, for lower-resolution displays. |

If a `dataUrl` fetch fails, the app falls back to the last successful response cached in
`localStorage`, and finally to the bundled sample data — it never goes blank. An "Showing
cached data" badge appears whenever it's not showing a fresh fetch.
